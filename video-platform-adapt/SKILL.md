# 一条录屏 → 三平台可直发成片

## 先明确这个 skill 解决什么

**真正要修的几乎从来不是"格式"。** 格式是最容易的一层（一条 ffmpeg 命令的事）。
发出去会翻车的通常是这四件：

1. 响度太低（−30 LUFS），手机外放听不见
2. 结尾混进了录制事故（截图工具栏、通知、鼠标乱晃）
3. 整屏录屏左右一大片黑，压到 1080p 后文字只有 10px，手机上根本看不清
4. 可变帧率，上传后音画不同步

所以判断顺序永远是：**信息能不能传达 > 观感 > 格式合规**。别把格式当验收终点。

---

## 铁律

1. **源文件一个字节都不动。** 开工先 `md5 -q SRC` 记下来，收尾再比一次。`build.py` 在输出路径等于源路径时直接拒绝执行。
2. **任何数字都要能复现，或标明来源。** 开场卡、标题、简介里出现的每个数，要么来自 `probe.py` 的测量，要么从成片里逐轮读出来。**凭记忆写数字必翻车**（真发生过：卡片写 300ms，实际区间 238–429ms）。
3. **只给一个平均值最容易被挑。** 给"中位数 + 区间 + 最差那轮是什么情况"。
4. **裁切前先问：删掉哪一侧，观众还信这是真的？** 再算像素。

## 第 0 步：自检（30 秒，别跳过）

```bash
python3 scripts/doctor.py
```

一条命令回答"这台机器还缺什么"：python / ffmpeg / ffprobe / libx264+aac / 五个必需 filter / Pillow / 中文字体 / 端到端最小编码（真编一段 0.5s 再解码）。每项失败都给能直接抄的修复命令，**有阻塞项时退出码非 0**。

最容易踩的一条：`python3` 指向的解释器和装了 Pillow 的那个往往不是同一个。报告里会打 `sys.executable`——看到 `No module named 'PIL'` 先核对这一行，别急着重装。

## 五步正片流程

### 第 1 步：体检

```bash
python3 scripts/probe.py SRC.mov --json /tmp/probe.json
```

读六项，其他都是背景信息：

| 项 | 判据 | 动作 |
|---|---|---|
| 帧率 | 标称 vs 均值差 > 5%，或间隔跨度 > 1.4× | VFR → `--fps 30` 转 CFR |
| 响度 | 低于 −20 LUFS | 必须归一化到 −16 |
| 开头静音 | 首段静音 > 0.5s | `--start` 截到静音结束前 0.2s（保留一个动作起点） |
| 片中长静音 | > 8s 且画面仍在变 | **不要当废片截掉**，那是"无解说但有信息" |
| 空白边距 | 左右/上下空区 > 20% | 裁掉，等于免费放大文字 |
| 尾部亮元素 | 末 15% 出现底部亮色新元素 | 疑似录制事故，截到首现时刻前 1.5s |

`probe.py` 还会给出各画幅的 `--crop` 建议值，以及每档的代价（切掉多少像素 / 文字放大几倍）。

### 第 2 步：做五个决定

**每个决定都必须落到具体数值，不能停在"看着差不多"。**

1. **起止点**：`--start` / `--end`。原则：开头不要纯静止；结尾不要事故、也不要在信息刚更新完就断。
2. **画幅与裁切**：`--crop W:H:X:Y` + `--fit RATIO --height H`。裁切是"牺牲哪一侧"的取舍，见铁律 4。
3. **平台版本**：至少出两个（竖 9:16 或 3:4 + 横 16:9）。见 `references/platform-specs.md`。
4. **开场卡**：要不要加。**判断依据是"这条片子会不会被当成剪辑过的演示"**——会，就加；不会，别加（3 秒静音是成本）。
5. **文案**：标题、短标题、简介、话题。简介必须补上画面里放不下的证据（被裁掉的地址栏、命令、仓库名）。

### 第 3 步：编码

```bash
# 竖版 3:4（视频号），带 3 秒开场卡
python3 scripts/build.py SRC.mov -o out_3x4.mp4 \
    --start 3.8 --end 157 --crop 1360:1722:820:242 --fit 3:4 --height 1440 \
    --card card_3x4.png --card-dur 3

# 横版 16:9（B站）
python3 scripts/build.py SRC.mov -o out_16x9.mp4 \
    --start 3.8 --end 157 --crop 3024:1701:0:242 --fit 16:9 --height 1080
```

`build.py` 已经固定了四件事，不用再操心：CFR 转换、两遍法响度归一化（先量后算、线性不压动态）、H.264 level 按宏块数自动选、开场卡与正片一次性重编码。

开场卡面用 `scripts/card.py`：

```bash
python3 scripts/card.py --ratio 3:4 -o card_3x4.png \
    --line "本机真机录屏 · 未剪辑 · 未加速" \
    --headline "它听出你说完 → 它开口" \
    --big "300ms" \
    --note "10 轮实测中位数 · 区间 238–429ms" \
    --foot "听出你说完本身还要约 0.5 秒"
```

上面这组文字是**格式示例**，里面的数字和结论必须换成你这次实测的——照抄就是铁律 2 的反面教材（pitfalls 第 12 条）。

### 第 4 步：验收

`build.py` 结束会自动调 `verify.py`；手动跑：

```bash
python3 scripts/verify.py out.mp4 --src SRC.mov --start 3.8 --card-dur 3
```

六项全绿才算完：完整解码 0 错误 / 流参数合规（h264 high·yuv420p·aac 48k·moov 前置）/ 帧数=时长×帧率 / 响度目标±1.5LU / **音画偏移等于开场卡时长** / 无纯黑场。

**音画同步这一项最关键**，它是唯一能抓住"拼接把声音提前了"的检查，而那种错误不报错、能播放。它用包络互相关对齐（不是找"第一个说话点"，那个方法在真实素材上会误判，见 pitfalls 第 16 条）。

### 第 5 步：交付

- 用 `present_files` 交付成片，**推荐的那一版放第一位**（通常是竖版：信息流占屏大、文字清楚）
- 文案按 `references/platform-specs.md` 的模板，三平台语气分开写
- 明确列出剩下必须人做的事：上传、封面、标题、等审核。**不要假装自己能发**

## 三个必须亲自看画面的时刻

脚本只会报警，判断得看画面。别省这三步：

1. **确认尾部事故**：抽最后 8 帧拼图，确认工具栏/虚线框一帧都不剩。`probe.py` 说 ✅ 也要看一眼，它是启发式。
2. **确认裁切没切内容**：编码后抽 1 帧，**专门检查最右和最左边缘有没有半截文字**（如括号「）」被切掉）。
3. **确认手机上能看清**：把成片某帧缩到 1080 宽看文字是否还认得。录屏里 10px 的字，在手机上是灰块。

## 边界

- **不做**：内容剪辑、配音、字幕烧制、画面美化、补拍。只做"把已有素材变成能发的东西"。
- **不替用户拍板**：发不发、发哪个标题、要不要砍掉尾段。给选项 + 代价，让他选。
- **不追求平台上限**：按安全区打，见 `references/platform-specs.md`。
- **适用素材**：屏幕录制、演示录屏、带解说的长视频。实拍素材（无黑边、无 UI）在第 1 步的"空白边距""尾部亮元素"两项上会误报，跳过这两项，其余照用。

## 依赖在哪（为什么这个 skill 装完就能跑）

| 类型 | 具体 | 存放 |
|---|---|---|
| 知识型（随 skill 分发） | 六项判据、画幅取舍、H.264 level 宏块规则、loudnorm 四参数、16 条坑 | 本文件 + `references/` |
| 工具型（声明，不内联本体） | ffmpeg ≥ 6（需 libx264 / loudnorm / ebur128 / silencedetect / anullsrc）、Pillow ≥ 9 | `doctor.py` 报版本、路径、缺项修法 |
| 环境资产 | **没有**——不需要 API key、账号、在线服务，全程本地 | — |

工具装不上不是"跑一半才发现"：第 0 步会点名卡在哪一项。同理，这个 skill 不依赖任何第三方 skill；图表类、发布类能力属于别人的活，这里只管"素材 → 可直发成片"。
