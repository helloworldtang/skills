# 踩过的坑（都在这条链路上真实发生过）

每条格式：**现象** → **根因** → **判据/处方**。遇到同类问题先按这里对一遍，别重新试错。

---

## 一、编码与拼接

### 1. 用 `-c copy` 拼接开场卡，画面正常但声音提前了 1.9 秒

- **现象**：`ffmpeg -f concat -c copy` 拼"开场卡.mp4 + 正片.mp4"，两个文件各自解码都正常，拼完的成片画面也在对的位置，但音频比应有时刻早了约 1.9s。**没有任何报错**。
- **根因**：AAC 编码器有 priming（编码器前导）样本，`-c copy` 直接把两个独立的 ADTS/MP4 音频段首尾相接，第二段的音频时间戳起点比视频早。
- **判据**：不能用"能不能播放""有没有报错"判断拼接成功；**必须量"说话起点"**。`verify.py --src --start --card-dur` 就是干这个的：源素材首个说话起点 + 卡片时长，应等于成片的首个说话起点，容差 0.15s。
- **处方**：开场卡与正片**一次性重编码**（走 `filter_complex` 的 `concat` 滤镜），不要 `-c copy`。顺带也避免了两代编码的画质损失。

### 2. H.264 level 选低了，部分播放器和平台不认

- **现象**：1920x1246 用 `-level 4.1` 编码，本地能播，但这是不合规的流。
- **根因**：level 的上限是**宏块数**，不是像素数。`ceil(1920/16) × ceil(1246/16) = 120 × 78 = 9360` 宏块，超过 L4.1 的 8192 上限 → 需要 L5.0。同理 1080x1920 = 68×120 = 8160 刚好卡进 L4.1。
- **判据**：`宏块数 = ceil(w/16) × ceil(h/16)`；`宏块/秒 = 宏块数 × fps`。两个都在上限内才合规。
- **处方**：`build.py` 内置 `pick_level()` 自动算，别手写。常见结果：1920x1080→4.1、1080x1440→4.0 或 4.1、1080x1920→4.1、1920x1246→5.0。

### 3. 标称 120fps、实测均值 49.5，帧间隔在 16/24/25ms 之间抖动

- **现象**：Mac 录屏产出的是 VFR（可变帧率）。`r_frame_rate` 写 120，`avg_frame_rate` 是 49.5，逐帧时间戳的间隔不固定。
- **根因**：录屏按画面变化出帧，静止时不产帧。
- **判据**：`ffprobe -select_streams v:0 -show_entries frame=best_effort_timestamp_time` 算逐帧间隔，p5–p95 跨度超过中位数的 1.4 倍就是 VFR。也可以直接看标称 fps 与均值 fps 差异 > 5%。
- **处方**：`fps=30` 强制转 CFR。`verify.py` 会用"帧数 == 时长 × 帧率"复核是否真的转成了 CFR（只写参数不算数）。

## 二、音频

### 4. 响度 −30.8 LUFS，手机外放几乎听不见

- **现象**：录屏自带的系统声/麦克风声非常小，峰值只有 −15.2dB。
- **根因**：录屏工具不做出厂响度归一化。
- **判据**：`loudnorm` 报的 `input_i`。**低于 −20 LUFS 就必须处理**；目标 −16 LUFS / −1.5 dBTP（信息流平台通用）。
- **处方**：**两遍法**——第一遍量出 `input_i / input_tp / input_lra / input_thresh`，第二遍带 `measured_*` + `linear=true` 做线性增益，不压动态。`build.py` 自动做这一步。

### 5. ⚠️ 最容易被误判的一条：响度归一化之后，用固定阈值测静音会误报

- **现象**：验证"开场卡之后说话起点是否对齐"时，用 `silencedetect=noise=-35dB` 测成片，报出"3 秒就有声音了"，看起来像严重错位。实际完全对齐。
- **根因**：线性增益 +14.7dB 把**底噪一起抬高**了。源素材开头 1.88s 的"静音"里峰值只有 −40dB 左右，抬完变成 −25.9dB，已经高于 −35dB 阈值 → 被判成有声。
- **判据**：**不要用绝对阈值跨文件比较**。两个处方（`verify.py` 用的是第二个）：
  1. 换成更高的阈值（−22dB）重测，并**比较两条音频的相对偏移**，而不是绝对值；
  2. 阈值按各自文件的峰值自适应：`th = clamp(max_volume - 12, -50, -10)`，这样增益变化被抵消。
- **教训**：这类"看起来是音画错位、其实是测量方法错"的假警报，比真错误更浪费时间。先怀疑测法。

### 6. 片子没有旁白时，会对"哪段是静音"判断失误

- **现象**：整条片子只有现场的麦克风收音和播报声，144.7–157.0s 有约 12 秒无人说话但画面还在刷新指标。
- **判据**：先看 `probe.py` 报的"片中最长静音"；超过 8 秒且画面仍在变化 → 是"无解说但有信息"，**不要当成废片截掉**。若画面已静止，才是该收尾。
- **处方**：留给用户决定要不要牺牲尾部指标刷新换节奏。别自作主张。

## 三、画面与裁切

### 7. 录屏尾部混进了截图工具栏和虚线选区

- **现象**：最后 2.4 秒出现 macOS 截图工具的白色工具栏 + 虚线框。
- **根因**：录屏过程中触发了截图快捷键/工具。
- **判据**：`probe.py` 的"尾部与画面稳定性"会逐秒采样底部 18% 条带的平均亮度，与基线差异 > 20 就报警，并给出首现时刻。**白色工具栏在深色背景上非常显眼，这个方法很稳。**
- **处方**：截到首现时刻之前 1.5s。同时**逐帧看最后 8 帧**确认没残留。

### 8. 画幅左右各有约 870px 全黑空区，内容栏只占 42% 宽

- **现象**：3024x1964 的整屏录屏，浏览器窗口只占中间一条。直接缩到 1080p，文字只剩 10px 左右，手机上根本看不清。
- **根因**：整屏录屏 ≠ 内容。
- **判据**：`probe.py` 的"画面内容边界"用边框众数色 + 阈值算出内容外接框，并给出占宽/占高比例。**内容占宽 < 70% 就该裁。**
- **处方**：按内容框裁，等于免费放大文字。裁完文字能放大 2 倍以上。

### 9. 裁到 16:9 会切掉整排核心 UI

- **现象**：想把 3024x1964 裁成 16:9，要么切顶部、要么切底部。
- **判据**：**先算哪一侧是"证据"**。这条片子的底部有"验收三式/下拉框/开麦按钮/指标行"——那是整个视频要证明的东西，不能动；顶部是浏览器标签栏和地址栏。所以裁顶部。
- **处方**：`crop=3024:1701:0:242` 恰好是精确 16:9，零变形零黑边。代价：`localhost:8000` 地址栏不在画面里（那正是"真机"的强证据），所以在文案里补一句。
- **通用判据**：**先问"删掉哪一侧，观众还能相信这是真的"**，再算像素。

### 10. 9:16 的意外好处：卡片预览裁切

- **现象**：小红书瀑布流卡片按 3:4 居中裁切预览。
- **判据**：如果内容区裁出来是 ~1368px 高、居中放在 1080x1920 里，那么 3:4 卡片窗口（1440px）正好完整包住它 → **卡片预览不裁内容，点开又是全屏沉浸**，不用二选一。
- **处方**：做 9:16 时，先看内容高度，让内容落在画面垂直居中的 ~71% 区域内。

## 四、流程与沟通

### 11. "格式合规"不等于"能发"

- 一条片子可能格式全对但发出去是事故：响度听不见、结尾有录制事故、文字小到看不清。
- **真正的判断顺序**：信息能不能传达 > 观感 > 格式合规。格式是最容易的一层，别把它当验收终点。

### 12. 开场卡上的数字必须从成片里逐轮读出来

- 出现过一次：凭记忆在卡片上写"300ms"，实际成片 10 轮是 238–429ms、中位 298。
- **处方**：卡片上的任何数字，都要么来自 `probe.py` 的测量，要么从成片帧里逐轮 OCR/读出来，并写明"区间 + 中位数"。**只给一个平均值最容易被挑。**
- 顺带：卡片里表述要**和画面 UI 用同一套词**。UI 写"判停成立之后"，卡片就别写"你说完"，否则读者一对照就发现口径不一致。

### 13. 源文件一个字节都不能动

- 每次开工先 `md5 -q SRC` 存到一边，收尾再比一次。
- `build.py` 里有硬保护：输出路径等于源路径直接拒绝执行。

### 14. 平台正文/简介的字数限制比想象中紧

- 上传时的描述框、B站简介都有字数上限，且**中文按字符算**。
- **处方**：文案先写"一句话结论 + 三条依据 + 话题标签"，控制在 300 字内；长文另发，别塞进简介。

### 15. 开场卡边界处 AAC 会加一个 20ms 的瞬态（实测 −13dB）

- **现象**：开场卡（数字静音）切到正片的那一瞬间，解码成 PCM 后能看到一个约 20ms、峰值 22%（−13dB）的突发。**同一滤镜链输出 PCM 时是完全干净的零**，只有 AAC 才有。
- **已排除**：不是 `concat` 的问题（纯 concat + PCM 输出干净），不是数字静音与底噪之间的台阶（把开场卡换成 −60dB 粉噪，瞬态照旧）。加了 50ms 淡入也没消掉。
- **结论**：这是 ffmpeg 原生 AAC 编码器在这类"长时间静音 → 有内容"边界上的编码伪影，属已知代价，**不影响音画同步**（互相关实测偏移 0.00s）。
- **处方**：能接受就接受（听感是很轻一声"嗒"）。要彻底消掉，可试 `libfdk_aac`，或把开场卡时长对齐到 AAC 帧边界（1024 样本 = 21.33ms 的整数倍，如 2.987s / 3.008s）——**但会引入 10ms 级的音画偏差，得自己权衡**。
- **重要**：正因为有它，**不能用"首个醒来的音频点"去判断音画同步**，见下条。

### 16. 音画同步别拿"首个说话点"当锚点，要用包络互相关

- **走过的弯路**：先用 `silencedetect` 找"静音结束"当锚点。结果源片报 1.22s、成片报 3.00s，算出 −1.22s 的假错位。原因有三层：① 源片本身有 −35dB 上下的杂波，锚点会落在毛刺上；② 阈值随峰值自适应，两个文件选的阈值不同，锚点必然不同；③ 上面第 15 条的 20ms 瞬态会被判成"声音开始"。
- **正确做法**：算两条音频的 10ms 步长 RMS 包络，在期望位移 ±0.6s 内做归一化互相关，取相关最大的位移。增益、单点杂波、编码瞬态都不影响，只看整体起伏。
- **判据**：位移与开场卡时长的偏差 ≤ 0.12s，且相关系数 > 0.5。相关系数低说明两段根本不是同一内容（源文件给错了）。
- **必须做负向测试**：故意传错 `--card-dur`，确认它真的会 FAIL。不会失败的检查等于没做。
- **两个衍生坑**（都在自测里踩到）：
  1. **稳态音频的互相关是无效的**。纯音、恒定噪声（无旁白的片子只剩环境声）包络没有起伏，相关峰不尖锐，相关系数天然低于 0.5——那不是"内容不一致"。判据：源包络的变异系数（`std/mean`）< 0.05 → 降级为提醒，别判失败。
  2. **窄搜索窗只够判"对不对"，不够说"错多少"**。在 ±0.6s 窗口里找最佳位移，真错位 3s 时会给出一个假的 +1.0s（窗口边缘的局部峰）。所以不通过时要放宽到整片再搜一次，把真实位移一并报出来——否则用户看到"偏差 −0.5s"会以为只差半秒。

## 五、环境（换台机器才暴露）

### 17. 装得上但跑不起来：`python3` 不是装了 Pillow 的那个

- **现象**：同一条命令在 A 机器上跑得好，B 机器上 `ModuleNotFoundError: No module named 'PIL'`。或者更隐蔽：Pillow 在，但中文字体找不到 → 文字退成方块，**不报错**。
- **根因**：`python3` 是个多义符号——系统自带（Xcode/CLT）、homebrew、pyenv、conda 各有一套 site-packages。系统 python 通常没装 Pillow。
- **判据**：先看 `doctor.py` 打的 `sys.executable`，确认是哪个解释器；再看字体项报的命中路径。
- **处方**：① 用绝对路径的解释器执行（或 `uv run --with pillow python3 ...`）；② 字体不在 `FONT_CANDIDATES` 里就补一条路径——注意**新版 macOS 已没有 `/System/Library/Fonts/PingFang.ttc`**，`Hiragino Sans GB.ttc` 是可靠的兜底（实测渲染正常）。Pillow 找不到字体时不会报错，只会画方块，所以这一项必须验"中"字的实际宽度，见 `doctor.py` 的 `check_font()`。
