# 最小复现装置：把复杂系统降噪成单变量实验

## 核心思想

**问题在复杂系统里，验证不该在复杂系统里。** 把嫌疑机制用一段话写清楚（结构 +
时序 + 触发方式），然后新建一个最小项目只复刻这一条主链路。跑出来的结论只有两种，
都有行动价值：

- **复现了** → 机制坐实，直接在最小项目上修到绿（迭代快、无副作用），再把修法回移植。
- **没复现** → 排除该机制，怀疑转向其他层——这一步同样省时间，避免在错误的方向上深挖。

它不是"写个 demo 看看"的随手行为，而是受控实验：变量只有嫌疑机制本身。

## 何时用（判定条件，同时满足）

1. bug 小而局部，能指着一个机制说"我怀疑是它"；
2. 全系统复现成本高：要真实数据/屏幕录制权限/特定窗口状态，或干扰因素太多；
3. 嫌疑机制可被独立复刻：不依赖半个系统的隐式状态。

不满足时（比如怀疑点本身就是"系统全局状态"）别硬套，直接在全系统上二分排查。

## 步骤

1. **写清嫌疑机制**：一段话，含结构（窗口/对象关系）、时序（什么事件触发什么收尾）、
   预期异常（会响两声/会崩溃/会闪一下）。写不清 = 还没到建装置的时候。
2. **单文件复刻**：swiftc / tsc 单文件编译（见 references/harness_template.swift），
   只抄嫌疑主链路，其余全部砍掉。抄的时候**保真优先于简洁**：styleMask、window level、
   canBecomeKey、事件处理顺序这些细节常常就是机制的一部分。
3. **进程内驱动**（关键决策，见下表）。
4. **时间戳日志**：每个关键节点（播放/收尾/拆窗/事件返回）打 `CACurrentMediaTime()`
   日志，事件序和延迟一目了然。
5. **对照判读**：加/去嫌疑细节各跑一遍，确认因果而非巧合。

## 驱动方式选型

| 方式 | 权限 | 保真度 | 适用 |
|---|---|---|---|
| CGEvent 合成（post 到系统） | 需辅助功能权限，**无权限时静默失败**（不报错！） | 完整（走 hit-testing） | 已授权环境、鼠标路径必须真实时 |
| `NSApp.sendEvent`（进程内构造 NSEvent） | 无需权限 | 高（走真实 AppKit 分发，但**绕过 hit-testing**） | 大多数场景首选 |
| 直接调目标函数 | 无 | 低（绕过整个事件分发） | 只验算法/纯逻辑时 |

CGEvent 静默失败验证法：post 一个 mouseMoved 到已知坐标，对比 `NSEvent.mouseLocation`
是否真的变了。没变 = 没权限。

## 保真度清单（结论打折的地方）

装置没复刻的东西要列出来，写进结论：

- sendEvent 不经过 hit-testing → 鼠标落点路由相关的结论要打折；
- 没有 TCC 权限弹窗、没有其他窗口争抢、没有真实输入设备的事件流；
- 复刻是"抄的"，抄漏的细节就是盲区（所以步骤 1 的机制描述要先行）。

## 实证案例（同一方法三次独立场合）

1. **macOS 截图工具确认音"响两声"**：复刻 borderless nonactivating 面板 + 子窗口工具栏
   + 延迟一拍拆窗，进程内 sendEvent 驱动 Enter/点击 → 装置只响一声 → 排除窗口机制，
   怀疑转向音效文件本身 → 最终实锤是系统音 Pop.aiff 自带双击结构。
2. **工具栏 ✓ 按钮被裁出面板**：swiftc 单文件编译 ToolbarPanel + 依赖，离屏渲染
   （cacheDisplay）出 PNG 看子视图 frame，无需起完整应用。
3. **选区四向可调验证**：swiftc 驱动合成 CGEvent（key/move/drag）+ 扫描线步进检测
   （帧差法被活屏内容污染不可用）。

三个案例的共性：问题小、主链路清晰、全系统验证又贵又吵。

## 已知坑

- swiftc 编译 top-level 的 `DispatchQueue.main.asyncAfter {...}` 尾随闭包会撞
  DispatchWorkItem 重载，包一层 `func after(_ delay:, _ block:)` 消掉；
- NSPanel 复刻时 `isReleasedWhenClosed = false` 别忘（否则 close 后悬垂访问）；
- 装置放 /tmp 下用完即弃，别混进项目仓。
