# 微信小游戏事件上报（We分析注册）全流程

> 实测验证：2026-10-29（We分析 `wedata.weixin.qq.com` `/mp2` 版本 UI，基于一个小游戏上线日的完整注册实操）。本 skill 的存在原因：此环节最容易犯的错是**拿过时路径/存档指路**——同一个后台 2026 年内就换过两次入口。**使用本 skill 时如界面与描述不符，以用户当前截图为准，先改本 skill 再指路。**

## 触发时机

用户说「注册事件 / 埋点上报 / We分析注册 / 事件上报 / reportEvent 没数据」等。

## 平台契约（先读，全是实测踩过的坑）

1. **入口只有一个**：`wedata.weixin.qq.com`（We分析独立平台，用小游戏绑定的微信扫码）。
   - mp.weixin.qq.com 后台「统计/数据分析」菜单里**没有**事件管理（旧「自定义分析→新建事件」入口已失效）。
   - `weanalysis.weixin.qq.com` 域名不存在（DNS NXDOMAIN）。
2. **路径（2026-10-29 实测）**：左侧「**数据管理 → 上报管理**」→「**新建元事件**」（三步向导；列表页也可「批量新建」「新增上报」）。
3. **上报类型**：`wx.reportEvent` 前端调用 = 选「**前端上报**」。
4. **事件 ID 必须与代码逐字一致**（区分大小写）：代码里 `wx.reportEvent('memory_warning', {...})`，平台就填 `memory_warning`。ID 建成后置灰不可改。
5. **属性全局唯一、加错基本删不掉**（官方警告「成功添加后仅无任何应用关系才可删除」，且被事件引用后连删都删不掉）。所以：**一律优先在「现有属性」下拉里选已有的；确认缺失才走「新增属性」**。
6. **默认 12 个属性自动上报**（app_state 等），不要在自定义属性里重复添加。
7. **数据 T+1**：当天注册，次日才能在事件分析里按属性维度看。「今日上报次数 0」当天属正常，不要误判为上报链路故障。
8. 基础版免费够用；「实时数据」等模块是专业版专属（按日均打开次数计费），小体量项目不碰。
9. 属性 ID 限英文小写字母/数字/下划线，64 字符内；数据类型选**数值**（可看均值/分布）或**字符串**（枚举/文本）——选错类型后期看不了分布。
10. 日常巡检可用手机端「We分析」小程序。

## 操作步骤（逐步点击版）

1. 开 `wedata.weixin.qq.com` → 扫码 → 选定小游戏（首次需开通，选**基础版/免费**）。
2. 左侧 **数据管理 → 上报管理**。
3. 点 **「新建元事件」**（或列表页「新增上报」），进入第一步表单：
   - **事件名称**：中文名
   - **事件 ID**：英文 ID，与代码 `wx.reportEvent` 的第一个参数逐字一致
   - **事件说明**：选填（建议写，后人会感谢你）
   - **上报类型**：**前端上报**
4. 「自定义属性」旁点 **「+ 添加」** → 弹窗「添加自定义属性」：
   - 默认「现有属性」→「选择属性」下拉里找目标属性 ID → 选中 → 添加
   - 下拉里**没有**目标属性时才切「新增属性」：属性名称（中文）、**属性 ID（与代码 data 里的 key 逐字一致）**、数据类型、描述
5. 保存/下一步走完向导（后续步骤为参数确认/完成页，无关键决策）。
6. 重复 3-5 建完所有事件。
7. **次日验证**：We分析「数据分析 → 行为分析 → 事件分析」里点开新事件，能按自定义属性拆维度 = 全链路通。

## ⚠️ 两条铁律（比步骤更重要）

1. **先查实际状态，再断言缺什么**：让用户在事件管理列表检索框里搜一遍事件 ID——文档/runbook 里记录的注册状态会过期（实测案例：某事件 10-17 已注册，文档仍写"待注册"，导致误判重做）。
2. **报后台操作路径前，先看用户当前界面截图**：We分析 UI 版本会漂，本 skill 的路径带实测日期戳；与用户界面不符时，以截图为准、更新 skill、再指路。

## 事件与属性清单模板（每个项目维护自己的单一事实源）

在 skill 或项目文档里维护一张总表，新增埋点先查表、注册完更新表——否则必然出现"代码在上报、平台没注册、报表永远空白"或"属性重复新建"。

| 分类 | 事件 ID | 名称 | 属性（类型） |
|---|---|---|---|
| 变现 | `ad_request` | 广告请求 | kind(字符串), scene(字符串) |
| 变现 | `ad_result` | 广告结果 | kind, scene, result |
| 对局 | `start_round` | 开始对局 | mode, round_index(数值) |
| … | … | … | … |

**示例（一个休闲小游戏的完整清单，含 18 事件）**：

- 变现：`ad_request{kind,scene}`、`ad_result{kind,scene,result}`
- 对局：`start_round{mode,round_index}`、`finish_round{mode,score,combo,popped,round_index}`、`round_bg{mode,score,seconds,round_index}`、`tutorial_done{seconds}`、`first_phrase{mode}`
- 增长/挽留：`launch_source{from}`、`revive_offer{choice}`、`revive_granted{mode}`
- 兴趣：`lb_view{tab}`、`share_click{scene}`、`combo_milestone{combo}`、`pause_action{action}`、`achievement_unlock{id}`、`skin_switch{id}`
- 哨兵：`memory_warning{level}`、`loop_error{msg}`、`touch_error{msg}`

属性命名建议全项目统一复用（mode/score/combo/id/msg/level/seconds/tab/action/choice…），新事件先查属性库再决定是否新建。

## 新增事件的完整 checklist

1. **代码侧**：上报调用挂在**离散动作**上（点击/结算/里程碑瞬间），禁止进帧循环或高频路径；事件名/属性 key 定稿。
2. **平台侧**：按上面步骤注册；属性先查现有库，缺了才新增。
3. **登记**：更新事件清单单一事实源（本 skill 或项目文档）。
4. **验证**（T+1）：事件分析里看计数 >0、属性维度可拆。
5. **对账口径**（广告类）：平台侧拉取量 ≈0 且 ad_request>0 → 平台/填充问题；拉取量 ≈0 且 ad_request=0 → 代码触发链断。

## 历史坑记录（为什么本 skill 长这样）

- **静默黑洞**：埋点代码一直在、从未注册、从未上报——`wx.reportEvent` 不注册=报表永远空白且无任何报错。这是本 skill 存在的第一原因。
- **路径漂移 ×3**：连续三次给错注册路径（mp 后台旧「自定义分析」入口失效；知识库存档路径与新版 UI 不符；漏了「自定义属性」配置步骤导致用户卡在表单）→ 引出「以用户截图实测为准」铁律。
- **清单漏列**：某哨兵事件在文档里漏列两个月，代码一直在静默上报 → 引出「事件清单单一事实源」纪律。
- **状态过期**：收尾时断言"4 个事件全部待注册"，实际其中 1 个早已注册（文档旧状态无人更新）→ 引出「先查平台列表再断言」铁律。
